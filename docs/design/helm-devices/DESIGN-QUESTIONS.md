# helm-devices -- Design Questions

> Non-obvious design questions that must be resolved before implementation.
> Each question names specific Rust types/traits, identifies competing design forces,
> and has no obvious single correct answer.
>
> Already-resolved decisions (Q60--Q71) are not repeated here.

## Domain 1: Device Modeling Infrastructure

**1.1. `Device::read()` takes `&self` but `clear_on_read` registers require mutation -- what is the interior mutability strategy?**

The LLD-device-trait shows `Device::read(&self, offset, size) -> u64` while the register_bank! macro generates `mmio_read(&mut self, ...)` for `clear_on_read` registers. The current design punts on the bridge with a note about `Cell`/`RefCell`/`UnsafeCell`. The choice matters because `RefCell` introduces a runtime borrow check on every MMIO read in the hot loop, `Cell` only works for `Copy` types (insufficient for `VecDeque<u8>` FIFOs), and `UnsafeCell` with manual safety arguments breaks Rust's aliasing model if the device is ever accessed from `HelmEventBus` callbacks during a read. The decision ripples through every device implementation and cannot be changed without a breaking API revision.

**1.2. How does `register_bank!` handle banked register sets where the active bank is selected by a control register?**

ARM's GIC Redistributor has registers that are banked per-PE, and many SoC peripherals have register pages selected by a bank-select field in a control register (e.g., UART's DLAB bit selects between IER/DLL at offset 0x01). The current macro grammar supports `read_only`/`write_only` split-function registers at the same offset, but has no syntax for N-way banking where the dispatch depends on runtime state. The tension is between keeping the macro grammar simple (device author handles banking in `on_read_*` hooks manually) versus adding a `banked_by = CTRL.BANK_SEL` clause that generates the dispatch automatically but makes the macro significantly more complex and harder to reason about at compile time.

**1.3. Should `MmioHandler::mmio_write()` accept `&mut Uart16550` directly, or should the device be passed as `&mut dyn DeviceCallbacks`?**

The generated `mmio_write(&mut self, offset, size, val, device: &mut Uart16550)` hard-codes the concrete device type, making the macro expansion device-specific. This prevents a single `MmioHandler` implementation from being reused across devices that share the same register layout but differ in side-effect behavior. The alternative -- a `trait DeviceCallbacks` with `on_write_*` methods and passing `&mut dyn DeviceCallbacks` -- enables reuse but introduces vtable dispatch on every register write in the hot loop and loses type safety on the hook method set. A third option uses a generic parameter `mmio_write<D: RegisterHooks>(&mut self, ..., device: &mut D)` which monomorphizes but still requires the hooks trait to be defined independently of the macro.

**1.4. When `Device::write()` triggers a side effect that needs to schedule a future event, how does the device obtain an `Arc<EventQueue>` reference?**

The HLD states `helm-devices` depends only on `helm-core` and has no dependency on `helm-event`. But a UART write that starts a baud-rate-timed transmission needs to schedule an `EventQueue` callback. The device cannot hold an `Arc<EventQueue>` field without adding `helm-event` to `helm-devices`' dependency list. The alternatives are: (a) break the dependency constraint and add `helm-event`, (b) define a `trait TimerCallback` in `helm-core` that `helm-event` implements (dependency inversion), (c) store the `Arc<EventQueue>` in the device's opaque `data` field via `Any` downcasting at `finalize()` time so the type never appears in `helm-devices` signatures, or (d) have the device fire a `HelmEventBus` synchronous event and let `World` translate it into an `EventQueue` entry. Each option trades dependency purity against ergonomics and hot-loop performance.

**1.5. What happens when two `register_bank!` declarations in the same device need overlapping `on_write_*` hooks that share mutable state?**

A GIC Distributor has a register bank for priority registers and a separate bank for enable registers, but writing to an enable register must re-evaluate pending interrupts using the priority values. If each bank is a separate `register_bank!` invocation generating a separate struct, the `on_write_enable()` hook needs mutable access to the priority bank's state. This creates a borrow conflict: the macro's generated `mmio_write` already holds `&mut self` on the enable bank while the hook tries to read the priority bank. The design must decide whether `register_bank!` supports multi-bank coordination natively (and how), or whether multi-bank devices bypass the macro and implement `Device::read/write` manually.

**1.6. Should `ParamSchema` validation be enforced at Python attribute assignment time, at `realize()` time, or both?**

The LLD-device-registry shows `ParamSchema::validate()` called before the factory function. But the Python layer allows attribute assignment at any time before `elaborate()`. If validation is deferred to `realize()`, the user discovers errors late (only when `build_simulator()` runs). If validation runs at assignment time, it requires the Python class to hold a reference to the `ParamSchema` and run type checks on every `__setattr__`, which complicates the Python class injection model because the embedded Python string currently has no schema awareness. The `Param.Int` annotations are documentation-only. The tension is between early error detection and implementation complexity in the PyO3 binding layer.

**1.7. How does `register_bank!` handle registers wider than 32 bits?**

The current macro generates `u32` fields for each register and `u32` parameters for `on_write_*` hooks. But ARM system registers (e.g., `TTBR0_EL1`) are 64-bit, and some device register banks have 64-bit data registers (e.g., AXI DMA descriptor addresses). The macro needs a width qualifier per register (`reg ADDR_HI_LO @ 0x10 is u64`), which changes the generated field type, the accessor mask widths, the serde serialization format, and the hook signatures from `(old: u32, new: u32)` to `(old: u64, new: u64)`. The question is whether this is a per-register qualifier, a per-bank default, or whether the macro should always use `u64` internally and narrow at the accessor level -- each choice has different performance and ergonomic implications.

**1.8. What is the checkpoint format compatibility contract for `register_bank!`-generated serde impls?**

Adding or removing a register field from a `register_bank!` invocation changes the generated struct's serde layout, breaking checkpoint compatibility. The LLD shows a `CKPT_VERSION` field that the device author must bump manually. But this is error-prone and does not help with automated checkpoint migration. The tension is between simplicity (manual version, device author's responsibility) and robustness (macro-generated schema hash, automatic detection of breaking changes, optional migration function). The decision also affects whether `bincode` (non-self-describing, fast, compact) or `serde_json`/`postcard` (self-describing, more resilient to field reordering) is the right checkpoint serialization format.

**1.9. Can `Device` trait objects be safely sent between threads for future multi-hart parallel simulation?**

The `Device` trait requires `Send` but the current LLD uses `RefCell` for interior mutability in `mmio_read`, which is `!Sync`. In a future multi-hart simulation where different harts may access the same device concurrently (e.g., two CPUs both writing to a shared UART's MMIO region), `RefCell` panics on concurrent borrow. Switching to `Mutex<RegisterBank>` adds lock overhead on every MMIO access. The architectural question is whether MMIO accesses to the same device from different harts should be serialized by the `MemoryMap` dispatch layer (so the device never sees concurrency), handled by per-device locking (so the device is `Sync`), or forbidden at the type level (devices are `!Sync`, one hart per device, duplicated devices for multi-hart).

**1.10. How should `write_1_to_clear` interact with `on_write_*` hooks -- does the hook see the raw write value or the post-W1C-logic value?**

For a `write_1_to_clear` register, writing `0x05` to a register that currently holds `0x07` should clear bits 0 and 2, leaving `0x02`. The `on_write_*` hook receives `(old: u32, new: u32)`. If `new` is the raw write value (`0x05`), the device author must re-implement the W1C logic in the hook. If `new` is the post-W1C value (`0x02`), the hook cannot distinguish "user wrote 0x05 to clear bits" from "user wrote 0x02 directly" for logging/tracing purposes. The decision affects every device that uses W1C status registers (which is nearly every interrupt-capable device).

## Domain 2: Built-in SoC Devices (ARM-centric)

**2.1. Should the ARM GIC-v3 Distributor, each Redistributor, and the ITS be separate `Device` implementations sharing state via `Arc<Mutex<GicState>>`, or a single monolithic `Device` with internal offset-based dispatch?**

The GIC-v3 has three distinct MMIO frames: the Distributor (GICD, 64KB), one Redistributor per PE (GICR, 128KB each), and optionally an Interrupt Translation Service (ITS, 128KB). In real hardware these are separate address regions. Making them separate `Device` impls that share `Arc<Mutex<GicState>>` mirrors hardware boundaries and enables independent mapping in `MemoryMap`, but introduces lock contention when a Redistributor read must consult Distributor state (e.g., checking GICD_CTLR.ARE_NS). A single monolithic device avoids locking but requires `MemoryMap` to support mapping one device at multiple non-contiguous address ranges, which the current `region_size() -> u64` API does not support.

**2.2. CPU system registers like `CNTPCT_EL0` (timer counter) and `MPIDR_EL1` (processor affinity) -- are these modeled as `Device::read()` calls via MMIO, as fields in `ArchState`, or as a separate `SysRegDevice` trait?**

Some system registers are pure CPU state (MPIDR is hardwired per-PE), some are shared device state (CNTPCT reads the system counter device), and some are both (ICC_* registers access GIC CPU interface state). Modeling all sysregs as `ArchState` fields bloats the register file with device-specific state. Modeling them as MMIO reads to a `Device` adds dispatch overhead on every `MRS` instruction. A hybrid approach where the ISA executor dispatches sysreg accesses through a `SysRegHandler` trait (which can be either inline ArchState access or a device read) adds a new trait to the system. The choice affects the `helm-arch` <-> `helm-devices` dependency direction.

**2.3. For the ARM SMMU (System MMU), should the stage-1/stage-2 page table walk be implemented in the SMMU device or delegated to `helm-memory`'s existing TLB/MMU infrastructure?**

The SMMU performs address translation using page tables in guest memory. `helm-memory` already implements page table walking for the CPU's MMU. Re-implementing the walk logic inside the SMMU device duplicates complex code (4KB/16KB/64KB granules, multi-level tables, ASID/VMID tagging). But sharing the walk engine means the SMMU device needs a dependency on `helm-memory` internals, violating the `helm-devices` isolation principle. Additionally, the SMMU walk may have different TLB invalidation semantics (TLBI by VMID vs by ASID) and different fault reporting paths (SMMU event queue vs CPU synchronous exception). The question is where the walk code lives and how it is shared without coupling.

**2.4. The ARM Generic Timer's `CNTPCT_EL0` must return a monotonically increasing counter value -- should this read the `VirtualClock` directly, or go through a `Device::read()` to a system counter device?**

If `CNTPCT_EL0` reads `VirtualClock::current_tick()` directly from the ISA executor, it is fast but couples `helm-arch` to `helm-engine`'s clock implementation. If it reads via a `Device` MMIO path to a `SystemCounter` device, it adds MMIO dispatch overhead on every timer register access (which guest OSes do frequently for timekeeping). The `TimingModel` complicates this further: in `Virtual` mode, the counter increments per instruction; in `Interval` mode, it increments by the IPC estimate; in `Accurate` mode, it tracks real pipeline cycles. The counter device must behave differently depending on the timing model, but `helm-devices` has no knowledge of `TimingModel`.

**2.5. ARM PSCI (Power State Coordination Interface) manages CPU power state transitions (CPU_ON, CPU_OFF, CPU_SUSPEND) -- is this a `Device` that talks to the engine, or built-in engine logic?**

PSCI is invoked via SMC/HVC instructions, not MMIO. It operates on the simulation's hart scheduling (powering a CPU on means starting its instruction stream; powering off means stopping it). Making PSCI a `Device` requires the device to have a handle to the engine's `Scheduler` to add/remove harts from the run queue -- a dependency that goes the wrong direction (`helm-devices` -> `helm-engine`). Making it engine-built-in means PSCI logic is hardcoded and cannot be replaced by a custom implementation. The alternative is a `trait PowerController` in `helm-core` that the engine implements and the PSCI handler calls, but this adds another trait to the already long list.

**2.6. The GIC-v3 LPI (Locality-specific Peripheral Interrupt) tables live in guest DRAM -- the GIC must read them via a memory access path. Should this go through `MemInterface`, through `MemoryMap`, or through a direct `FlatMem` reference?**

LPI configuration tables (GICR_PROPBASER, GICR_PENDBASER) point to guest physical memory containing per-LPI priority and enable state. When an LPI is received (e.g., via MSI-X), the GIC must read these tables to determine routing. Going through `MemInterface` (the CPU's memory path) is semantically wrong -- the GIC is a bus master, not a CPU. Going through `MemoryMap` means the GIC read appears as an MMIO transaction and could trigger `HelmEventBus` callbacks. A direct `FlatMem` reference bypasses all dispatch but breaks the abstraction layers. This is the same fundamental question as DMA device memory access (Domain 4, Q4.5) but with the additional constraint that GIC table reads are on the interrupt delivery critical path.

**2.7. How should CPU interface registers (ICC_*) be modeled when GIC-v3 uses system register access (no memory-mapped CPU interface)?**

In GICv3, the CPU interface registers (ICC_IAR1_EL1, ICC_EOIR1_EL1, ICC_PMR_EL1, etc.) are accessed via MRS/MSR instructions, not MMIO. They are logically part of the GIC but accessed as CPU system registers. This creates a layering problem: the ISA executor in `helm-arch` must dispatch these register accesses to the GIC device in `helm-devices`. The executor cannot hold an `Arc<GicCpuInterface>` without adding a `helm-devices` dependency to `helm-arch`. The options are: inject the GIC CPU interface as a `Box<dyn SysRegHandler>` into the executor at `elaborate()` time, add it as an `ExecContext` method, or model it as a special MemInterface region. Each option has different coupling and performance characteristics.

**2.8. When the ARM Generic Timer comparator fires (CNTP_CVAL_EL0 <= CNTPCT), the timer must inject a virtual interrupt into the CPU -- how does this cross from `EventQueue` callback context to CPU interrupt injection?**

The timer device schedules an `EventQueue` event at the comparator tick value. When the event fires, the callback needs to assert the timer's `InterruptPin`. But `InterruptPin::assert()` calls `InterruptSink::on_assert()` synchronously, which for a GIC modifies the GIC's pending state and potentially calls `cpu_irq_out.assert()`. The `EventQueue` callback executes between instruction steps, when `ArchState` may be in an intermediate state. The question is whether `EventQueue` callbacks are guaranteed to run at instruction boundaries (safe to modify CPU interrupt state) or at arbitrary points in the step cycle (requiring deferred interrupt injection via a flag that the CPU checks at the next boundary).

**2.9. Should watchdog timer devices (SP805, for example) be able to trigger a system-wide reset, and if so, what is the mechanism?**

A watchdog timeout should trigger a platform reset -- calling `reset()` on every `SimObject` in the `World`. But a `Device::write()` (the watchdog's register timeout handler) cannot call `World::reset_all()` because the device has no reference to `World`. The device could fire a `HelmEventBus::Custom("watchdog_reset")` event and have the engine subscribe to it, but this makes reset handling implicit and hard to trace. Alternatively, the device could return a `DeviceAction::Reset` enum from `write()`, but that changes the infallible `write()` signature. The decision extends to any device that can trigger system-level actions (power-off, warm reset, cold reset).

**2.10. For multi-socket/multi-cluster ARM platforms, how does the GIC's affinity routing (MPIDR-based) interact with `World`'s flat object namespace?**

GIC-v3 routes interrupts based on PE affinity levels (Aff3.Aff2.Aff1.Aff0 encoded in MPIDR). The GIC Distributor must map from an affinity value to the correct Redistributor/CPU interface. In `World`, CPUs are flat objects like `"board.cpu0"`, `"board.cpu1"`. There is no built-in concept of clusters, sockets, or affinity hierarchies. The question is whether affinity routing is a GIC-internal lookup table (configured by the platform Python script), a `World`-level topology API (`World::affinity_map()`), or derived from object naming conventions. This also affects SMMU stream ID to device mapping, and PCI requester ID to device mapping.

## Domain 3: Dynamically Loadable Devices

**3.1. Can a `.so` plugin be hot-reloaded at runtime (unloaded and reloaded with a new implementation) without stopping and restarting the simulation?**

The current `DeviceRegistry` stores `libloading::Library` handles in `_libs: Vec<Library>` to prevent `dlclose`. Hot-reload would require: (a) destroying all device instances created from the old plugin, (b) `dlclose`-ing the old `.so`, (c) `dlopen`-ing the new `.so`, and (d) recreating devices with the new factory. Steps (a) and (d) require the `World` to track which devices came from which plugin. The fundamental tension is between developer iteration speed (hot-reload avoids restarting long-running simulations) and safety (Rust function pointers from the old `.so` become dangling after `dlclose`; any `Arc<dyn InterruptSink>` held by other devices that points into the old plugin's code is now a use-after-free). Even `catch_unwind` cannot protect against a vtable pointing into unmapped memory.

**3.2. What is the minimum stable ABI surface that must survive Rust toolchain upgrades without requiring plugin recompilation?**

The current ABI check is a single `HELM_DEVICES_ABI_VERSION: u32`. But Rust has no stable ABI -- the layout of `Box<dyn Device>`, vtable ordering, and `HashMap`/`Vec` internals can change between compiler versions. A plugin compiled with rustc 1.78 and loaded into a host compiled with rustc 1.82 may have incompatible vtable layouts for `Device`, `InterruptSink`, and `SimObject`. The options are: (a) accept same-compiler-version only (the gem5 approach), (b) define a C-ABI-only boundary with `extern "C"` wrappers around every trait method (massive boilerplate, no trait objects cross the boundary), (c) use `abi_stable` crate to enforce a stable ABI for specific traits, or (d) use a message-passing protocol (protobuf/flatbuffers) across the `.so` boundary. Each option has dramatically different ergonomics and performance profiles.

**3.3. Can plugin devices and built-in devices be mixed transparently in the same platform configuration, with identical lifecycle behavior?**

Built-in devices register via `inventory::submit!` (linker-level self-registration) while plugins register via `helm_device_register()` (C-ABI call). The `DeviceDescriptor` is the same struct in both paths. But subtle differences may emerge: built-in devices can use workspace-internal types that are not part of the ABI surface, built-in devices are constructed in the same address space and can use zero-cost trait objects, and built-in devices' `ClassDescriptor` is populated at startup while plugin descriptors arrive later. The question is whether a Python config script can write `helm_ng.Uart16550()` without knowing or caring whether the UART is built-in or from a plugin, and whether checkpoint/restore works identically for both.

**3.4. What isolation is possible for a buggy plugin without full process isolation?**

A plugin that writes to a wild pointer can corrupt the host simulator's heap. `catch_unwind` only handles Rust panics, not segfaults or memory corruption. Process isolation (running the plugin in a child process with shared memory for MMIO) adds IPC latency on every `Device::read/write` call -- unacceptable for the hot loop. The alternatives are: (a) accept the risk (the QEMU/gem5 approach -- plugins run in-process, bugs crash everything), (b) use WebAssembly (WASI) as the plugin runtime (sandboxed, but limited to what wasm can express and adds significant overhead), (c) use `seccomp` to restrict plugin syscalls after loading, or (d) put only the MMIO dispatch behind a `jmp` guard page so that wild writes within the plugin's region are caught. The answer determines the plugin trust model for the entire project.

**3.5. When a plugin's embedded Python class string declares `__init__` parameters that conflict with or diverge from its `ParamSchema`, whose definition wins?**

The `DeviceDescriptor` has both a `param_schema: fn() -> ParamSchema` and a `python_class: &str` field. The Python class declares `clock_hz: Param.Int = 1_843_200` and the ParamSchema declares `.int_default("clock_hz", 1_843_200, ...)`. These must agree, but nothing enforces it. If the Python class declares a parameter `baud_rate` that has no corresponding `ParamField` in the schema, Python `__init__` accepts it silently but the factory function never sees it. If the schema has a required parameter `dma_channel` that the Python class omits, Python construction succeeds but `realize()` fails with `MissingParam`. The question is whether the loader should parse the Python class string and cross-validate against the schema at load time, or accept the divergence risk.

**3.6. How should plugin devices provide checkpoint migration when the plugin is upgraded between the save and restore operations?**

A user saves a checkpoint with plugin v1.0 (3 registers) and restores with v1.1 (4 registers, one new). The checkpoint blob was serialized by v1.0's `register_bank!`-generated serde impl. The v1.1 serde impl expects the new field and deserialization fails. The device author needs a migration path, but `checkpoint_restore(data: &[u8])` gives raw bytes with no schema metadata. Options: (a) version tag + manual migration code in `checkpoint_restore`, (b) plugin exports a `fn migrate_checkpoint(old_version: u32, data: &[u8]) -> Vec<u8>` function, (c) use self-describing serialization (JSON/msgpack) so missing fields get defaults, or (d) require checkpoint format stability as a plugin contract (breaking changes require a new device name). This intersects with question 1.8 on checkpoint format.

**3.7. Should the `DeviceRegistry` support device type aliasing or versioned device names for backward compatibility?**

If a plugin renames `uart16550` to `ns16550a` in a new version, existing Python configs that reference `helm_ng.Uart16550()` break. The registry currently uses exact string matching on `name: &'static str`. Adding aliases (`DeviceDescriptor::aliases: &'static [&'static str]`) or versioned names (`"uart16550@1.0"`) complicates the registry lookup, the Python class injection (which class name wins?), and checkpoint restore (checkpoints store the device type name). The tension is between strict naming (simple, unambiguous) and evolution-friendly naming (supports rename/deprecation without breaking users).

**3.8. How should a plugin declare that it requires a specific host capability (e.g., KVM acceleration, raw socket access, GPU passthrough)?**

Some device plugins may need host OS resources beyond normal memory allocation -- a virtio-net device might need raw socket access, a GPU passthrough device needs VFIO. The current `DeviceDescriptor` has no way to declare these requirements. The plugin either panics at `realize()` time (bad UX) or returns `DeviceError::InitFailed` with a message the user may not understand. Options: (a) add `required_capabilities: &[&str]` to `DeviceDescriptor` and check at load time, (b) have the factory function return a structured `Err` that the Python layer presents as a user-friendly diagnostic, (c) add a `fn check_requirements() -> Result<(), String>` to the descriptor that the loader calls before registration. The decision affects whether `load_plugin` can fail fast with good diagnostics vs failing late in `create()`.

**3.9. When multiple plugins export the same `HelmEventBus` event types, how is event type identity maintained across `.so` boundaries?**

`HelmEventBus` fires `HelmEvent` enum variants. If a plugin defines a `HelmEvent::Custom(String)` event and another plugin subscribes to it by string name, the dispatch works. But if a plugin defines its own enum variant (possible in a future extension), the host and plugin may disagree on enum discriminant values due to independent compilation. The question is whether `HelmEventBus` should restrict plugins to `Custom(String)` events only (losing type safety), define a plugin event registration protocol with runtime-assigned discriminants, or use a hash-based event ID system where the event type identity is a hash of the event name string rather than an enum discriminant.

**3.10. Should plugins be able to register new `Bus` trait implementations (e.g., a custom CAN bus), and if so, how does the `BusDevice` trait's `read_register/write_register` signature accommodate bus-specific protocols?**

The current `BusDevice` trait has `read_register(&self, reg: u8, size: usize) -> u64` which assumes register-based access. A CAN bus plugin needs message-based access (`send_frame(id: u32, data: &[u8])`) which does not fit the register model. The options are: (a) plugins cannot introduce new bus types (built-in only), (b) add a `BusProtocol` trait with an associated `Transaction` type that plugins implement (generic over the transaction shape), (c) make `BusDevice` have an `Any`-typed method `fn bus_transaction(&mut self, data: &dyn Any) -> Box<dyn Any>` that loses all type safety, or (d) define bus-specific `BusDevice` sub-traits (`CanBusDevice`, `UsbDevice`) that plugins can implement. Each option is a different point on the type-safety vs extensibility spectrum.

## Domain 4: Bus and Protocol Modeling

**4.1. For PCIe ECAM config space reads, does the `PciBus` device decode the target BDF (Bus/Device/Function) itself, or does `MemoryMap` split the ECAM window into per-function regions?**

The current LLD-bus-framework shows `PciBus` receiving the full ECAM offset in `Device::read(offset)` and decoding BDF internally via `decode_ecam()`. But `MemoryMap` could instead map each PCI function as a separate 4KB region (the ECAM spec guarantees 4KB per function), which would let `MemoryMap::lookup()` return the per-function device directly -- bypassing the `PciBus` decode entirely. The tension is: PciBus-internal decode mirrors hardware (the host bridge is the decoder), but MemoryMap per-function mapping enables direct device dispatch without the PciBus intermediary. The choice affects whether `PciBus` is just configuration infrastructure or an active participant in every PCI config access.

**4.2. When a PCIe device sends an MSI-X interrupt (a memory write to a GIC ITS/LPI address), should this write go through the normal `MemoryMap` MMIO dispatch path, or through a dedicated MSI routing shortcut?**

In real hardware, MSI-X is a posted memory write to a physical address (typically in the GIC ITS's MMIO region). Routing it through `MemoryMap` means the MSI write looks like any other MMIO write -- it hits the GIC ITS's `Device::write()`, which processes it as an LPI. This is correct but introduces two levels of MMIO dispatch (PCIe device -> MemoryMap -> GIC ITS device) plus `HelmEventBus::MemWrite` event overhead for every interrupt. A shortcut (`PciBus::route_msi(target_addr, data) -> InterruptSink::on_assert()`) bypasses the memory system entirely, which is faster but skips MemoryMap access checks, breaks observability (the write is invisible to `HelmEventBus`), and diverges from the hardware model. The answer depends on whether MSI-X fidelity or interrupt delivery performance matters more.

**4.3. For I2C multi-master arbitration, if two simulated I2C master controllers (both `I2cBus` devices) try to claim the bus simultaneously, who arbitrates?**

The current `I2cBus` implementation is a standalone device with no concept of bus sharing. In real hardware, I2C multi-master is resolved by bit-level arbitration on the SDA line. In simulation, two `I2cBus` instances accessing the same set of I2C slave devices would need a shared `I2cBusArbitrator` that serializes access. But this requires a shared mutable object between two `Device` impls, which violates the design principle that devices do not share mutable state. The options are: (a) forbid I2C multi-master in simulation (single master only), (b) model the arbitrator as a separate `Device` that both masters route through, (c) use `Arc<Mutex<I2cBusState>>` shared between master devices (set up at `elaborate()` time). Option (c) works but makes the arbitration decision in a `Mutex` critical section on the hot path.

**4.4. Should AMBA AXI backpressure (READY/VALID handshake signals) be modeled in the `Bus` trait, or should helm-ng collapse all bus transactions to zero-latency completion?**

In real AXI, a slave device can deassert READY to stall the master for N cycles. Modeling this in simulation means `Device::write()` cannot complete synchronously -- it must return a `Pending` status and the caller must retry or be stalled. This fundamentally changes the `Device::write()` return type from `()` to something like `Result<(), BusStall { ready_in_cycles: u64 }>`. Collapsing to zero-latency is simpler and correct for functional simulation, but prevents modeling of bus congestion, priority arbitration, and QoS that AXI supports. The decision affects whether helm-ng can model interconnect-level bottlenecks or only device-level behavior. The `TimingModel` parameter could make this decision per-accuracy-level: `Virtual` ignores backpressure, `Accurate` models it.

**4.5. When a DMA engine device needs to write to guest physical memory (e.g., scatter-gather DMA from a VirtIO disk), does it call `Device::write()` on the target memory region, or does it get a direct `MemoryMap` handle?**

A DMA engine is a bus master -- it initiates memory transactions. The current `Device` trait has `write(&mut self, ...)` for incoming writes, but no API for a device to perform outgoing writes. Options: (a) give the DMA device an `Arc<MemoryMap>` reference stored at `finalize()` time, allowing it to call `memory_map.write(addr, size, val)` directly; (b) define a `trait BusMaster` with `fn dma_write(&self, addr: u64, size: usize, val: u64)` that `World` implements and passes to devices at elaborate time; (c) route DMA writes through `World::mmio_write()` so they are observable via `HelmEventBus` and subject to SMMU translation; (d) give the device a `FlatMem` reference for raw memory access (bypassing MMIO dispatch and SMMU). The answer determines whether DMA is observable, whether SMMU can translate DMA addresses, and whether DMA is fast.

**4.6. How should PCI BAR (Base Address Register) window management work when a guest OS re-programs a BAR to a different physical address at runtime?**

The current design says `region_size()` is fixed (Q61), but BAR re-programming changes the base address, not the size. When a guest OS writes to a PCI config space BAR register, the PciBus must update `MemoryMap` to unmap the old region and map the new one. But `MemoryMap` may cache the `FlatView` and not expect runtime remapping. The `PciBus` device would need a `&mut MemoryMap` to call `unmap_device` + `map_device`, but holding `&mut MemoryMap` inside a `Device::write()` call creates a borrow conflict (the device is already borrowed mutably by the MMIO dispatch). This is the re-mapping problem: how does a device modify the memory map from inside a write handler?

**4.7. For SPI flash XIP (Execute-In-Place), the flash device is both a SPI slave (register-based command interface) and a memory-mapped read region (instruction fetch). How are these two views modeled?**

A QSPI flash controller has two modes: command mode (software writes commands via SPI protocol registers) and XIP mode (the flash contents are memory-mapped at a base address for direct CPU instruction fetch). In XIP mode, every instruction fetch to the flash address range must return flash data without going through the SPI command protocol. This requires the flash device to be both a `BusDevice` attached to an `SpiBus` and a `Device` mapped in `MemoryMap`. The question is whether one struct implements both traits, whether the QSPI controller creates a separate `MemoryRegion` for the XIP window (registered at `elaborate()` time and dynamically enabled/disabled), or whether the instruction fetch path has special handling for XIP regions.

**4.8. When a PCIe endpoint device signals a fatal error (SERR# / PERR#), how does this propagate through the bus hierarchy to the host bridge?**

PCI error signaling is hierarchical: an endpoint signals an error, the upstream bridge detects it, and it propagates to the root complex which may trigger a system-level NMI or machine check. The current `BusError` enum has `Timeout` and `Nack` but no error propagation model. Options: (a) add `BusError::Fatal { source: BusAddress }` and propagate through `Bus::bus_write()` return values, (b) use `InterruptPin` wiring (SERR# is essentially an interrupt), (c) fire a `HelmEventBus` event and let the platform handler decide what to do, or (d) model error signaling via the PCI config space AER (Advanced Error Reporting) capability register reads. The choice determines whether PCI error handling is a first-class feature or deferred.

**4.9. How should the `Bus` trait's `attach()` method handle hot-plug -- a PCIe device being added or removed while the simulation is running?**

PCIe supports hot-plug: a device can be electrically inserted or removed at runtime. The current design freezes the wiring graph after `startup()`. Supporting hot-plug requires: (a) `Bus::attach()` callable after `startup()`, (b) dynamic `MemoryMap` updates for BAR regions, (c) interrupt wiring changes (new device's MSI must be routable), (d) `HelmEventBus` notification so the guest OS driver can detect the insertion. The tension is between phase-frozen simplicity (all wiring at elaborate time, no runtime changes) and hardware fidelity (PCIe hot-plug is a real feature that guest OS drivers exercise). This question is closely related to Q4.6 (BAR re-programming).

**4.10. For USB, the host controller (xHCI) maintains a command ring and transfer rings in guest memory, polled via DMA -- should this polling be driven by `EventQueue` timers, by explicit `advance()` calls, or by a `Device::step()` method called every N CPU instructions?**

USB host controllers perform DMA to read transfer descriptors from guest memory without CPU involvement. In a functional simulation, the xHCI device must periodically check its rings for new work. Driving this via `EventQueue` timers is clean but requires choosing a poll interval (too fast wastes simulation time, too slow adds latency). A `Device::step()` method called every N instructions keeps the device progressing but adds overhead to the CPU hot loop for every device, not just USB. A third option is event-driven: the CPU writes to a doorbell register, and the xHCI only processes rings when notified. This last option is most efficient but requires the guest driver to cooperate (not all drivers ring the doorbell immediately). The choice applies to any device that performs background DMA polling (VirtIO, NVMe, network controllers).
